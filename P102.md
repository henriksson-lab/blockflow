# External Benchmark Plan For Selected Examples

Goal: turn the three most meaningfully different examples into fair external
benchmarks against frameworks already used in this repository's benchmark work,
and only where the workflow can be expressed naturally in that framework.

The priority order is:

1. `examples/object-3d-measurement`
2. `examples/colocalization`
3. `examples/wound-assay`

Do not optimize for winning a benchmark by narrowing semantics. The benchmark
should expose where Blockflow is fast, where it pays overhead, and where output
semantics differ.

## Shared Rules

- Keep Blockflow and reference outputs comparable, not necessarily identical to
  every package's native naming or metadata model.
- Use only previously compared framework families unless a later plan explicitly
  broadens the scope: CellProfiler, ImgLib2, OpenCV, scikit-image/SciPy and
  Dask-image.
- Do not add a reference just because the framework is popular. Add it only when
  the problem can be expressed directly and readably in that framework.
- Use deterministic synthetic fixtures first so correctness can be checked by
  exact or tight-tolerance comparisons.
- Add optional real-data benchmarks only after the synthetic benchmark is stable.
- Report wall time, in-process pipeline time where available, peak RSS, object
  or pixel counts, and semantic comparison status.
- Run at least two batch sizes: 10 images and 50 images.
- Keep all generated data and benchmark output under `.tmp/<example>/`.
- Add root `BENCHMARKS.md` rows only after the reproduction scripts are stable.

## 1. 3-D Object Measurement

Why this is worth benchmarking:

- It stresses labelled 3-D object measurements, physical spacing, bounding-box
  geometry and object-table output.
- It is meaningfully different from simple pixel filtering or 2-D segmentation.
- Under the current scope, the natural first target is scikit-image/SciPy.
  CellProfiler can be considered only if its 3-D measurement path is small and
  maintainable for this fixture.

Initial comparison target:

- Start with scikit-image/SciPy if `regionprops_table` or a similarly direct
  path can express the shared columns.
- Do not add ImageJ/Fiji, MorphoLibJ or SimpleITK in this pass; they are outside
  the framework set already compared in this repository.
- Do not add CellProfiler unless the workflow can be expressed as a small,
  natural pipeline with comparable 3-D measurement columns.

Implementation tasks:

1. Add `reference-skimage/` under
   `examples/object-3d-measurement/`.
2. Generate labelled 3-D fixture files on disk, preferably `.npy` or TIFF stack,
   instead of only in-memory fixtures.
3. Extend the Blockflow runner to read the same fixture files, or add a fixture
   generator that both runners use.
4. Compute comparable columns:
   - label,
   - voxel count,
   - bounding-box min/max,
   - physical bounding-box extents,
   - max voxel-center Feret diameter if the reference supports it.
5. If the reference does not support max Feret directly, compare only the shared
   columns and record Feret as Blockflow-only.
6. Add `scripts/run_reference.sh` and `scripts/run_benchmark.sh` timing/RSS
   collection.
7. Add a comparison tool if exact CSV diff is no longer appropriate.

Acceptance:

- 10-image and 50-image synthetic runs complete for Blockflow and the reference.
- Shared columns match exactly or within documented floating tolerance.
- Benchmark output records wall time, RSS and comparison status.

## 2. Colocalization

Why this is worth benchmarking:

- It stresses labelled two-channel reductions and derived measurement rows.
- It maps directly to CellProfiler MeasureColocalization and simple
  NumPy/scikit-image labelled reductions.
- Output semantics matter, so this benchmark is more informative than a raw
  two-array loop.

Initial comparison target:

- Start with scikit-image/SciPy/NumPy because the primitive labelled reductions
  are direct and already match the current example's Python reference style.
- Add CellProfiler only if MeasureColocalization can be configured on the same
  fixtures with a simple, maintainable pipeline and comparable output columns.
- Do not add ImgLib2, OpenCV or Dask-image unless a direct labelled
  colocalization expression is found; forcing them into this shape would
  benchmark glue rather than the framework.

Implementation tasks:

1. Add fixture-file generation for labels plus two intensity channels.
2. Extend the Blockflow runner to consume those fixtures, not only generate
   in-memory data.
3. Add a NumPy reference that computes:
   - per-label finite pair count,
   - sum A/B,
   - sum A²/B²,
   - sum AB,
   - Pearson,
   - overlap coefficient,
   - Manders M1/M2 using the same positive threshold.
4. Add optional CellProfiler workflow if the output columns can be mapped
   cleanly enough for comparison.
5. Add benchmark timing/RSS collection and a tolerant comparison script.

Acceptance:

- 10-image and 50-image synthetic runs complete.
- NumPy reference agrees with Blockflow on primitive sums and derived values.
- Any CellProfiler comparison documents expected naming/semantic differences.

## 3. Wound Assay

Why this is worth benchmarking:

- It is a compact segmentation-plus-summary workflow with clear image-level
  outputs.
- Relevant comparisons are easy for OpenCV and scikit-image/SciPy.
- It is useful for measuring pipeline overhead, batch execution and simple
  image-level reductions.

Initial comparison target:

- OpenCV and scikit-image/SciPy are both good fits: thresholding, morphology and
  area/profile summaries are direct.
- Dask-image can be added only if the same image-level workflow maps cleanly to
  chunked arrays without custom bookkeeping dominating the benchmark.
- Do not add CellProfiler unless a compact wound-area pipeline is natural enough
  to maintain.
- Do not add ImgLib2 unless the Java reference remains short and idiomatic.

Implementation tasks:

1. Add fixture-file generation for wound images, ideally 8-bit PNG/TIFF.
2. Extend Blockflow to read those images instead of only generating in memory.
3. Add reference implementation with the same threshold and morphology choices.
4. Decide whether the benchmark includes morphology cleanup. If yes, pin the
   structuring element and border policy.
5. Compare:
   - open area,
   - covered area,
   - open fraction,
   - per-column open profile.
6. Add timing/RSS collection for 10-image and 50-image batches.

Acceptance:

- Blockflow and reference outputs agree exactly for threshold-only mode.
- If morphology mode is added, differences are bounded and documented by border
  policy.
- `BENCHMARKS.md` can report wall time, RSS and semantic comparison status.

## Reporting

Once each benchmark is stable, add a section to `BENCHMARKS.md` with:

- benchmark purpose,
- reference software and version,
- hardware/date,
- batch size,
- wall time,
- peak RSS,
- key output counts,
- semantic comparison result,
- reproduction commands.

## Stop Point

Stop this pass when all three examples have at least one external reference
benchmark with reproducible 10-image and 50-image runs, or when one benchmark
reveals a missing Blockflow API that must be fixed before further comparison is
meaningful.
